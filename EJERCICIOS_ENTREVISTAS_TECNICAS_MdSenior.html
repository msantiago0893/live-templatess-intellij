Programa de lealtad — Clientes y puntos Entrevista técnica

Nota: Ejercicio de entrevista técnica Indra — para Banamex — mid sr

Caso de negocio

Una empresa cuenta con un programa de lealtad para sus clientes. Los clientes acumulan puntos por sus compras y posteriormente pueden canjearlos por beneficios. Se requiere desarrollar un microservicio para administrar clientes y sus puntos.

Entidad principal: Customer

CampoDescripción
idIdentificador único
customerNumberNúmero de cliente
nameNombre del cliente
pointsPuntos acumulados

Arquitectura esperada

  1. controller
  2. service
  3. repository
  4. entity

Ejemplo - Crear cliente

{
  "customerNumber": "0001",
  "name": "Juan Perez"
}

Ejemplo - Acumular puntos

{
  "points": 100
}

Ejemplo - Canjear puntos

{
  "points": 50
}

Reglas de negocio

  1. customerNumber es obligatorio.
  2. customerNumber debe ser único.
  3. name es obligatorio.
  4. Los puntos iniciales deben comenzar en cero.
  5. Los puntos a acumular deben ser mayores a cero.
  6. Los puntos a canjear deben ser mayores a cero.
  7. No se debe permitir que el saldo de puntos sea negativo.
  8. El cliente debe existir para poder acumular o canjear puntos.

Manejo de errores

  1. 404 cuando el cliente no exista.
  2. 400 para solicitudes inválidas.
  3. 409 cuando no existan suficientes puntos para realizar el canje.

Endpoints requeridos

MétodoEndpointDescripción
POST/customersCrear cliente
GET/customersConsultar clientes
GET/customers/{id}Consultar cliente por id
POST/customers/{id}/earn-pointsAcumular puntos
POST/customers/{id}/redeem-pointsCanjear puntos

Ejemplo de respuesta para puntos insuficientes

{
  "message": "Insufficient points"
}

Criterios de evaluación

  1. El proyecto compila y ejecuta correctamente.
  2. Persistencia funcional utilizando H2.
  3. Correcta separación de responsabilidades por capas.
  4. Uso adecuado de Spring Boot y JPA.
  5. Diseño REST.
  6. Validaciones y manejo de errores.
  7. Legibilidad y calidad del código.

Requerimientos técnicos

  • Persistir información utilizando H2.

Ejercicio 10 — API de notas médicas Intermedio

Caso de negocio

Una clínica necesita administrar sus pacientes y las notas médicas asociadas a cada uno. Se requiere desarrollar un microservicio para gestionar pacientes y notas médicas.

Entidad principal: MedicalNote (relación N:1 con Patient)

CampoDescripción
idIdentificador único
patientIdPaciente asociado
dateFecha de la nota
diagnosisDiagnóstico
treatmentTratamiento indicado

Entidad secundaria: Patient

CampoDescripción
idIdentificador único
dossierNumberNúmero de expediente (único)
nameNombre del paciente
birthDateFecha de nacimiento

Arquitectura esperada

  1. controller
  2. service
  3. repository
  4. entity

Ejemplo - Crear paciente

{
  "dossierNumber": "EXP-001",
  "name": "Ana Torres",
  "birthDate": "1990-05-15"
}

Ejemplo - Crear nota médica

{
  "date": "2026-10-01",
  "diagnosis": "Gripe común",
  "treatment": "Reposo y líquidos"
}

Reglas de negocio

  1. dossierNumber es obligatorio y único.
  2. name es obligatorio para el paciente.
  3. birthDate es obligatoria para el paciente.
  4. date es obligatoria para la nota.
  5. diagnosis es obligatoria.
  6. El paciente debe existir para crear notas médicas.
  7. Las notas deben estar asociadas a un paciente existente.
  8. No se pueden crear notas para pacientes eliminados.

Manejo de errores

  1. 404 cuando el paciente o la nota no exista.
  2. 400 para solicitudes inválidas.
  3. 409 cuando el dossierNumber ya esté registrado.

Endpoints requeridos

MétodoEndpointDescripción
POST/patientsCrear paciente
GET/patientsConsultar pacientes
GET/patients/{id}Consultar paciente por id
POST/patients/{id}/notesCrear nota médica
GET/patients/{id}/notesConsultar notas del paciente
GET/notes/{id}Consultar nota por id

Ejemplo de respuesta de error

{
  "message": "Patient not found"
}

Criterios de evaluación

  1. El proyecto compila y ejecuta correctamente.
  2. Persistencia funcional utilizando H2.
  3. Correcta separación de responsabilidades por capas.
  4. Uso adecuado de Spring Boot y JPA.
  5. Diseño REST.
  6. Validaciones y manejo de errores.
  7. Legibilidad y calidad del código.

Ejercicio 11 — Transferencias entre cuentas Avanzado

Caso de negocio

Un banco necesita permitir transferencias de dinero entre cuentas de sus clientes de forma segura y atómica. Se requiere desarrollar un microservicio para gestionar cuentas y transferencias.

Entidad principal: Account

CampoDescripción
idIdentificador único
accountNumberNúmero de cuenta (único)
ownerTitular
balanceSaldo actual

Arquitectura esperada

  1. controller
  2. service
  3. repository
  4. entity

Ejemplo - Crear cuenta

{
  "accountNumber": "1111222233",
  "owner": "Pedro Sanchez"
}

Ejemplo - Transferir

{
  "fromAccountNumber": "1111222233",
  "toAccountNumber": "4444555566",
  "amount": 150.00
}

Reglas de negocio

  1. accountNumber es obligatorio y único.
  2. owner es obligatorio.
  3. El saldo inicial debe comenzar en cero.
  4. El monto de la transferencia debe ser mayor a cero.
  5. La cuenta origen debe tener saldo suficiente.
  6. La cuenta origen y destino deben existir.
  7. La cuenta origen no puede ser igual a la cuenta destino.
  8. La transferencia debe ser atómica: si falla una parte, no se debe aplicar ningún cambio.

Manejo de errores

  1. 404 cuando alguna cuenta no exista.
  2. 400 para solicitudes inválidas (monto ≤ 0, origen = destino).
  3. 409 cuando el saldo sea insuficiente.

Endpoints requeridos

MétodoEndpointDescripción
POST/accountsCrear cuenta
GET/accountsConsultar cuentas
GET/accounts/{id}Consultar cuenta por id
POST/transfersRealizar transferencia

Ejemplo de respuesta de error

{
  "message": "Insufficient balance for transfer"
}

Criterios de evaluación

  1. El proyecto compila y ejecuta correctamente.
  2. Persistencia funcional utilizando H2.
  3. Correcta separación de responsabilidades por capas.
  4. Uso adecuado de Spring Boot y JPA.
  5. Diseño REST.
  6. Validaciones y manejo de errores.
  7. Legibilidad y calidad del código.
  8. Atomicidad en la transferencia.

Ejercicio 12 — Sistema de cupones de descuento Avanzado

Caso de negocio

Una tienda necesita crear cupones de descuento y aplicarlos a las compras de sus clientes. Se requiere desarrollar un microservicio para gestionar cupones.

Entidad principal: Coupon

CampoDescripción
idIdentificador único
codeCódigo del cupón (único)
discountPercentPorcentaje de descuento
activeActivo (true/false)
usedUsado (true/false)

Arquitectura esperada

  1. controller
  2. service
  3. repository
  4. entity

Ejemplo - Crear cupón

{
  "code": "DESCUENTO20",
  "discountPercent": 20
}

Ejemplo - Aplicar cupón

{
  "code": "DESCUENTO20",
  "purchaseAmount": 100.00
}

Reglas de negocio

  1. code es obligatorio.
  2. code debe ser único.
  3. discountPercent debe estar entre 1 y 100.
  4. active debe comenzar en true.
  5. used debe comenzar en false.
  6. No se puede aplicar un cupón ya usado.
  7. No se puede aplicar un cupón inactivo.
  8. El cupón debe existir para ser aplicado.
  9. purchaseAmount debe ser mayor a cero.

Manejo de errores

  1. 404 cuando el cupón no exista.
  2. 400 para solicitudes inválidas (porcentaje fuera de rango, monto ≤ 0).
  3. 409 cuando el cupón ya haya sido usado o esté inactivo.

Endpoints requeridos

MétodoEndpointDescripción
POST/couponsCrear cupón
GET/couponsConsultar cupones
GET/coupons/{id}Consultar cupón por id
POST/coupons/applyAplicar cupón a una compra

Ejemplo de respuesta de error

{
  "message": "Coupon already used"
}

Criterios de evaluación

  1. El proyecto compila y ejecuta correctamente.
  2. Persistencia funcional utilizando H2.
  3. Correcta separación de responsabilidades por capas.
  4. Uso adecuado de Spring Boot y JPA.
  5. Diseño REST.
  6. Validaciones y manejo de errores.
  7. Legibilidad y calidad del código.

Ejercicio 13 — Biblioteca con préstamos Avanzado

Caso de negocio

Una biblioteca necesita gestionar sus libros con múltiples ejemplares y permitir préstamos a sus usuarios. Se requiere desarrollar un microservicio para administrar libros, usuarios y préstamos.

Entidad principal: Loan (relación N:1 con Book y User)

CampoDescripción
idIdentificador único
bookIdLibro prestado
userIdUsuario que retira
loanDateFecha de préstamo
returnDateFecha de devolución
statusEstado (ACTIVO, DEVUELTO)

Entidad secundaria: Book

CampoDescripción
idIdentificador único
isbnISBN (único)
titleTítulo
authorAutor
copiesEjemplares disponibles

Entidad secundaria: User

CampoDescripción
idIdentificador único
emailEmail (único)
nameNombre

Arquitectura esperada

  1. controller
  2. service
  3. repository
  4. entity

Ejemplo - Crear libro

{
  "isbn": "978-84-204-1234-5",
  "title": "El Quijote",
  "author": "Miguel de Cervantes",
  "copies": 3
}

Ejemplo - Registrar préstamo

{
  "bookId": 1,
  "userId": 1
}

Reglas de negocio

  1. isbn es obligatorio y único.
  2. title y author son obligatorios.
  3. copies inicial debe ser mayor o igual a cero.
  4. El libro debe tener al menos un ejemplar disponible para prestar.
  5. El usuario y el libro deben existir para registrar un préstamo.
  6. loanDate se asigna automáticamente.
  7. status comienza en ACTIVO.
  8. Al devolver, copies debe incrementarse en 1.
  9. No se puede prestar un libro sin ejemplares disponibles.

Manejo de errores

  1. 404 cuando el libro o usuario no exista.
  2. 400 para solicitudes inválidas.
  3. 409 cuando no hayan ejemplares disponibles.

Endpoints requeridos

MétodoEndpointDescripción
POST/booksCrear libro
GET/booksConsultar libros
POST/usersCrear usuario
GET/usersConsultar usuarios
POST/loansRegistrar préstamo
POST/loans/{id}/returnDevolver libro
GET/loansConsultar préstamos

Ejemplo de respuesta de error

{
  "message": "No copies available"
}

Criterios de evaluación

  1. El proyecto compila y ejecuta correctamente.
  2. Persistencia funcional utilizando H2.
  3. Correcta separación de responsabilidades por capas.
  4. Uso adecuado de Spring Boot y JPA.
  5. Diseño REST.
  6. Validaciones y manejo de errores.
  7. Legibilidad y calidad del código.

Ejercicio 14 — Gestión de eventos con aforo limitado Avanzado

Caso de negocio

Una organización necesita crear eventos con un cupo limitado de asistentes y permitir la inscripción de participantes. Se requiere desarrollar un microservicio para gestionar eventos e inscripciones.

Entidad principal: Event

CampoDescripción
idIdentificador único
nameNombre del evento
dateFecha del evento
capacityCupo máximo
enrolledInscritos actuales

Arquitectura esperada

  1. controller
  2. service
  3. repository
  4. entity

Ejemplo - Crear evento

{
  "name": "Conferencia de Java",
  "date": "2026-11-15",
  "capacity": 50
}

Ejemplo - Inscribirse al evento

{
  "participantEmail": "ana@email.com",
  "participantName": "Ana Ruiz"
}

Reglas de negocio

  1. name es obligatorio.
  2. date es obligatoria.
  3. capacity debe ser mayor a cero.
  4. enrolled debe comenzar en cero.
  5. participantEmail y participantName son obligatorios para inscribirse.
  6. No se puede exceder el cupo máximo (enrolled < capacity).
  7. No se puede inscribir el mismo email dos veces al mismo evento.
  8. El evento debe existir para inscribirse o cancelar inscripción.

Manejo de errores

  1. 404 cuando el evento no exista.
  2. 400 para solicitudes inválidas.
  3. 409 cuando el cupo esté lleno o el participante ya esté inscrito.

Endpoints requeridos

GET/eventsConsultar eventos
GET/events/{id}Consultar evento por id
POST/events/{id}/enrollInscribirse al evento
DELETE/events/{id}/enroll/{email}Cancelar inscripción

Ejemplo de respuesta de error

}

Ejercicio 15 — Wallet digital con historial Avanzado

Caso de negocio

Una fintech necesita administrar billeteras digitales donde los usuarios pueden recargar dinero, realizar pagos y consultar su historial de transacciones. Se requiere desarrollar un microservicio para gestionar wallets y transacciones.

Entidad principal: Wallet

CampoDescripción
idIdentificador único
userIdUsuario propietario (único)
balanceSaldo actual
currencyMoneda (USD, EUR, MXN)

Entidad secundaria: Transaction

CampoDescripción
idIdentificador único
walletIdWallet asociada
typeTipo (RECHARGE, PAYMENT)
amountMonto
dateFecha de la transacción

Arquitectura esperada

  1. controller
  2. service
  3. repository
  4. entity

Ejemplo - Crear wallet

{
  "userId": "USER-001",
  "currency": "USD"
}

Ejemplo - Recargar

{
  "amount": 100.00
}

Ejemplo - Pagar

{
  "amount": 30.00,
  "description": "Pago de servicio"
}

Reglas de negocio

  1. userId es obligatorio y único (una wallet por usuario).
  2. currency es obligatoria y debe ser USD, EUR o MXN.
  3. balance inicial debe comenzar en cero.
  4. El monto de recarga debe ser mayor a cero.
  5. El monto de pago debe ser mayor a cero.
  6. No se puede pagar más que el saldo disponible.
  7. Cada operación debe generar una transacción en el historial.
  8. La wallet debe existir para recargar, pagar o consultar historial.

Manejo de errores

  1. 404 cuando la wallet no exista.
  2. 400 para solicitudes inválidas (monto ≤ 0, moneda inválida).
  3. 409 cuando el saldo sea insuficiente para el pago.

Endpoints requeridos

MétodoEndpointDescripción
POST/walletsCrear wallet
GET/wallets/{id}Consultar wallet
GET/walletsConsultar wallets
POST/wallets/{id}/rechargeRecargar
POST/wallets/{id}/payPagar
GET/wallets/{id}/transactionsHistorial de transacciones

Ejemplo de respuesta de error

{
  "message": "Insufficient balance"
}

Criterios de evaluación

  1. El proyecto compila y ejecuta correctamente.
  2. Persistencia funcional utilizando H2.
  3. Correcta separación de responsabilidades por capas.
  4. Uso adecuado de Spring Boot y JPA.
  5. Diseño REST.
  6. Validaciones y manejo de errores.
  7. Legibilidad y calidad del código.
